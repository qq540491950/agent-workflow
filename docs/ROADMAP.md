## 一、ADK 侧(按相关性排序)

### 1. 会话持久化:`session/database`(GORM + SQLite)
- **现状**:每个 execute 新建 `session.InMemoryService()`(engine.go),ADK 会话事件
  历史不跨进程;Resume 靠自研 StateData 快照回放重建状态。
- **方向**:v1.7.0 自带 `database.NewSessionService(dialector)` + AutoMigrate,
  sessionID=exec.ID 的会话可天然跨重启存活;Resume 可重入原会话,
  StateData 手工回放与 syncNodeStates 兜底可大部分删除。
- **代价**:需引入 gorm + 纯 Go sqlite dialector(glebarez)依赖;引擎执行/恢复
  路径深度改动。
- **决策**:暂缓。现有恢复链路已经过跨进程崩溃恢复 E2E 验证(轮次 17/21),
  收益(会话历史查询)不抵回归风险;待 ADK v2 迁移时一并考虑。
  *轮次 37 的补充*:运行时状态写已收敛为「状态只走 CAS + 元信息不覆盖 state」
  且两者合成一条原子 SQL(见 `docs/OPTIMIZATION.md` 轮次 37),**恢复链路的
  状态裁决更可靠**,但"会话历史查询"这一收益本身没有变化 —— 决策不变。
  *轮次 46 的补充*:CAS 冲突现在**可观测**了(冲突时不发终态事件、改发
  `runtime.error` + 计数 `StateCommitFailures()`),"恢复后状态与事件流
  打架"这一类风险被关掉;但会话历史仍只存在于 `state_json` 快照里,
  收益本身没变 —— **决策不变**。
  *轮次 45 的补充*:会话状态快照(`state_json`)现在**按键分类脱敏**,
  结构化键原样保留 —— 恢复路径的语义不因脱敏而改变(这一点是这项收益
  仍不着急的另一个理由:改会话持久化要同时重做这层分类)。**决策不变**。

## 三、已确认的语义决定(勿当 Bug "修复")

- **DELETE 幂等**:删除不存在的资源返回 200(api/server_test.go 有断言)。
- **git 出口的脱敏与节点 output 出口同源**(第二十五轮 / 迭代 30 新增,`#330`):
  git 包的**五个出口**(`Status` / `Diff` / `Log` / `Commit` / `CurrentBranch`)
  一律过 `logx.Mask`(**键名 ∪ 值形态**)—— 与**节点 output 出口同源**
  (`logx/credential.go` 是形态规则的唯一来源)。
  **为什么比"只按值形态"严**:git 面板是**用户当前工作区**的实时视图,
  里面的 `.env` 低熵密码(`DB_PASSWORD=hunter2`)只有**键名规则**抓得住 ——
  值形态规则判它"不是凭据",但秘密照样明文出站。
  **与"制品出口"的差异是刻意的**:制品(`/api/executions/{id}/artifacts`)
  走**只按值形态**的规则 —— 制品是**已落库的历史快照**,要保住"改了哪
  一行"这个审计证据;两者规则**同源**,只是**严格度按出口不同**。
  **不要把 git 出口改回"只按值形态"** —— 那会让 `.env` 里的低熵密码
  明文出站(约定 8)。**也不要给工作流 git 节点(`Service.Run`)在本包内
  叠一层键名规则** —— 它的输出由应用层统一处理(节点 output → `logx.Mask`;
  制品 → 值形态规则),在本包再叠会与制品出口打架。
- **内部错误按 kind / code 映射状态码**(第二十五轮 / 迭代 30 新增,`#331`):
  `api` 层新增 `statusForError`(**先按 code 再按 kind**)——
  `DB_ERROR` / `INTERNAL` → **500**、`KindAgentError` / `KindProcessError`
  → **502**、`KindTimeoutError` → **504**;既有 4xx 映射**一条未动**
  (`NOT_FOUND`→404、`PAYLOAD_TOO_LARGE`→413、权限→403、其余→400)。
  **语义**:数据库锁死 / Agent 崩溃 / 超时与"用户填错了参数"**无关**,
  此前一律报 400 → 用户与监控无法区分,4xx 告警会被这类噪声淹没。
  **`INVALID_RESUME` / `INVALID_TRANSITION` 刻意保持 400**(不改成 409)——
  它们是**既有对外契约**(文档 + `api/cancel_semantics_test.go` 都在),
  改 409 是破坏契约;"改 409"这件事登记为待统一裁决的开放项。
- **CLI 空输出判失败**(第二十六轮 / 迭代 31 新增,`#336`):
  CLI **退出码 0 但 stdout 为空/只有空白**时,适配器**一律判失败**
  (错误带上 stderr 线索 —— 退出码 0 时 stderr 是**唯一**的诊断线索;
  拼接前先脱敏),**不得**返回"成功 + 空决策"。
  **理由是同一函数内的自相矛盾**:输出**被截断**早已是显式失败,
  而**信息量更少**的空输出却是成功 —— 两套口径打架。**更严重的是**:
  运行期的 `matchBranch` 在条件不匹配时**兜底走无条件分支** →
  路由**静默换道**,用户看不到任何异常(约定 14"该失败却成功")。
  **不要把它改回"空输出 = 成功"** —— 那等于给"CLI 崩了但退出码是 0"
  开了后门(写日志文件而非 stdout、被 wrapper 吞掉输出等都是真实形态)。
  **但"空输出"不等于"猜一个决策"** —— 约定 1 的"禁止字符串猜测"仍然
  成立,这次是**失败**而不是**静默成功**。
  **pi 侧是刻意的例外**:pi 的输出形态本就是自由文本(仓库自带示例
  工作流 `workflows/examples/coding-task.yaml` 的 plan / execute 节点靠的
  正是它)→ pi 侧改成"**成功但留痕**"(`Data["decision_missing"] = true`),
  **不判失败**(判失败会打断既有工作流形态);claude 侧可以判失败,
  因为**适配器自己**在提示词里要求了 JSON 决策。
- **全局状态键(decision/status/output)在并行分支内可能互相覆盖**:
  并行体决策请用 merge 节点读取节点级键(StatusKey/ResultKey);
  全局键的 ADK 会话合并由分支隔离机制处理,Go 层只保证无数据竞争。
- **非 JSON 的 Claude 输出不猜测 decision**(需求 §36 字符串匹配禁令)。
- **决策取值只校验形态,不枚举白名单**(轮次 39 新增,`agent.NormalizeDecision`):
  取值先去掉首尾空白并转大写,然后必须形如 `[A-Z][A-Z0-9_]*` 且不超过 64 字符;
  **不合法就不写 Decision**(绝不把怪值送进路由),改为在 `data` 里留
  `decision_invalid` / `decision_raw` 并在摘要里标注。
  **不枚举白名单是刻意的**:工作流允许自定义决策(如 `REFACTOR`),
  白名单会把合法用法判死。典型被拒形态是模型把提示词里的模板原样吐回来
  (`"APPROVED|REJECTED|CONTINUE|DONE|WAIT_USER"`)—— 这类值进路由会让
  条件永远不成立。
- **契约外状态一律 fail closed**(轮次 49 新增,`#176` / `#178`):
  Agent / Skill 返回的状态**不在契约内**(未知取值、空串)时**一律判失败**,
  绝不"落空即成功"。契约只有三个:`SUCCESS` / `FAILED` / `WAIT_USER`。
  归一的唯一来源是 `skill.NormalizeStatus` 与 `coreagent` 侧的同名口径
  (去空白 + 转大写)—— 外部实现返回 `"wait_user"` / `"Failed"` 是常态,
  不是异常。**这是刻意的 fail closed**:状态字段是外部实现的产物,
  项目无法枚举它的全部形态;把"不认识的"当成"成功",等于让任何一份
  拼错的实现静默放行(约定 14)。
  **它推翻了第三轮的口径** —— 第三轮曾把"契约外状态按成功处理(不猜)"
  当作刻意决定写进用例(`TestSkillStatusUnknownIsSuccess`)。**不要把
  第三轮那条用例当权威**:它保护的是一个后来被判定为违反约定 14 的决定。
  教训:把当前行为写进测试不等于该行为正确,钉住口径前先问"这口径对吗"。
- **未知配置键只警告不阻断**(轮次 50 新增,`#183`):
  节点配置里出现未被识别的键(`timeout_seconds` 拼成 `timeout_second`)时,
  校验期发 `UNKNOWN_NODE_CONFIG` **警告**并给编辑距离建议,**不报错**。
  理由:存量工作流里确实存在拼错的键,报错会让用户**打不开自己的老工作流**
  —— 那是"用户被自己的校验器挡住"(约定 13 的反面)。同样地,已废弃的键
  (`condition.expression`)只报"已废弃"、不报"未知",避免两条互相矛盾的提示。
  与之对照:**顶层**未知键与 `permissions` 错层级是**硬错误**
  (`DSL_UNKNOWN_KEY` / `DSL_MISPLACED_KEY` / `UNKNOWN_FIELD`)——
  那两处的后果是"设置没生效"或"权限收紧被悄悄放开",静默的代价更大。
- **有效权限 = 全局实时策略 ∧ 工作流 `permissions` 段(只收紧)**(第十轮新增,`#229` / `#240`):
  两条语义合在一起,是因为它们各自单看都会出事:
  ① **全局策略必须实时读取** —— 此前是执行**启动时**的快照 → 用户在运行中
     收紧权限,**对在跑的执行无效**。而"权限收紧"是安全操作,用户会**立刻
     期待它生效**(改完设置就以为在跑的节点也被限制了)。现在全局策略实时读取,
     收紧**立即对在跑的执行生效**;
  ② **`permissions` 段只能收紧,永远不能放宽** —— 此前覆盖段用"**替换**"语义,
     能把全局禁用**放开**。而适配器(`pi`)只看得到全局策略 → 同一个执行里
     **两处判定打架**:运行期节点检查说"可以写",适配器说"不能写"。
     现在覆盖段与全局策略**求交**(只收紧),**放宽尝试在校验期就报出**
     (`PERMISSION_OVERRIDE_LOOSENS`)。
  **这是刻意的 fail closed**:权限判定的两个来源(全局 / 工作流)必须给出
  **同一个结论**,否则"用户以为的收紧"就是假的。**不要把它改成"覆盖优先"** ——
  那等于把"工作流可以突破全局禁用"变成默认行为。
  **同样地,不要把全局策略改回快照** —— 那会让"运行中收紧"重新变成假的。
- **`mode` → 是否需要写权限只有一份来源**(第十一轮,`agent.ModeRequiresWrite`,**已进主干**):
  运行期的节点检查此前查 `execute|fix`,而 `pi` 适配器自己查 `execute|fix|submit`
  → `mode: submit` 的节点**不受工作流级 `permissions` 段约束**(适配器只看得到
  全局策略)。两份集合不一致 = 同一个执行里两处判定打架(与上一条同族)。
  现在**唯一来源**是 `agent.ModeRequiresWrite`,运行期与适配器共用。
- **值的形态规则只有一份定义**(第十二轮新增,`#245` / `#246`):
  此前仓库里有**两套并行的掩码规则**:`logx.Mask` / `logx.MaskValue` 按**键名**
  判定(`key=value` 形态),`agent.MaskCredentialValues` 按**值形态**判定(已知前缀 /
  JWT / PEM / 高熵长串),后者只在 2 处被调用 —— 两套语义不同、覆盖范围不同,
  于是同一个凭据在不同出口的结论**不一致**:"出口用哪套就漏另一半"。
  终审实测的 P0 正是这条缝:`Bearer eyJ…` 这种**没有键名**的裸值,
  键名规则不触发、值形态规则当时也不覆盖 → 原样落进 `execution_nodes.output`
  与 `executions.state_json`,并经**所有** API 出口(SSE / 执行详情 / 导出)
  流到前端。
  **现在的口径**:值的形态规则**只有 `logx/credential.go` 一份**
  (PEM 块 / JWT / webhook / 键名+值形态 / `Bearer`·`Basic` 方案 /
  裸值(已知前缀 · 严格高熵)),`agent.MaskCredentialValues` 降为**薄封装**;
  `logx.Mask` 升级为"**键名 ∪ 值形态**"。落库侧与读出口**各过一次** → 终态
  都是 `***` → **幂等**。
  **这是约定 13(同源)在"脱敏规则"这条轴上的落地** —— 此前它只覆盖
  "校验期与运行期"。**不要在别处再写一份形态判定**:`TestMaskValueShapeRuleIsSingleSource`
  断言两个入口**逐字节一致**,两份实现各自演化会立刻变红。
  **同时不要把两条规则的严格度合并成一条**:键名语境(有线索)门槛**宽松**
  (≥16 字符 + 字母 + 数字 + 大小写混合,或 ≥32 字符),裸值语境(没线索)门槛
  **严格**(≥24 字符 + 大小写混合 + 数字)—— 否则 git SHA、base64 测试夹具会被
  抹掉,毁掉 diff 的审计价值。这是**刻意的两种严格度,不是两份规则**。
- **形态 × 出口的覆盖矩阵必须逐格登记**(第十二轮新增,`#247`):
  "规则覆盖了哪些形态 × 哪些出口"此前**从来没被断言过** —— 改规则不会让
  任何测试变红,少一条规则也不会。终审的 P0 正是"**裸值形态 × 节点输出**"
  一个**组合**漏了,而当时没有断言能发现它。
  现在矩阵是**可执行的**(`TestCredentialShapeCoverageMatrix`,**17 形态** × 2 出口),
  **未覆盖的格子必须写清理由** —— 不许"默认都覆盖"。将来谁改门槛,矩阵立刻变红,
  取舍必须被**重新论证**一遍。
  **三条刻意保留的取舍**(登记在开放清单里,不是漏网):① **制品出口的低熵值
  不脱敏**(diff 里的 `password = "xxx"` 多半是代码/占位符,抹掉会毁掉审计
  证据;DB / API / 日志出口走键名规则,照常脱敏);② **高熵裸值的 24 字符门槛**
  (裸值语境没有线索,门槛必须严 —— 否则 git SHA、base64 测试夹具会被抹掉);
  ③ **驼峰标识符护栏**(**第二十九轮 / #342 收窄为五条**:起伏≥4 / 驼峰词序列 /
  词长≥2 / 每词含小写 / **数字段≤1 处** —— 旧口径"起伏≥4"对随机字符几乎
  必然满足,等于"高熵串豁免")。
  **保留第十轮的取舍**:代码标识符不误伤(`const token = getToken();` 逐字保留)——
  这正是驼峰护栏存在的理由,**收窄判据不许把它收没**。
- **路由依据与展示文本分离**(第九轮新增,`#205` / `#222`):
  `output` 既是**自由文本键**(值常带 CLI stderr 里的凭据 → 落库必须脱敏,
  约定 8),又是**条件变量**(条件表达式可以直接读它,约定 13 要求它的集合只有
  一份定义)。这两重身份带来一条口径差:实时路径在**原文**上求值,恢复路径在
  **脱敏副本**上求值 —— 根因**不止凭据形态**:`output` 的语义是"最近一次成功
  节点的输出",**分支内后续节点会覆盖它**,恢复时重算读到的是完全不同的值。
  **这不是"窄到无所谓"**:终审实测证明它是**可达的分支改变** —— 人批准 A 分支,
  恢复后走 B 分支(约定 14 同族:走错分支比崩溃更危险 —— 用户看不到任何异常,
  只看到"流程跑完了")。
  **收口方式**:路由一旦选定出口分支,这个选择就是本次执行的**既成事实** →
  记进**结构化**状态键 `route:<决策节点>:branch`(值是分支下标,枚举、不含
  自由文本、不落凭据),恢复时**回放**它,不再拿脱敏副本重新求值。
  **另外两条路都被否掉了**:把 `output` 排除出脱敏 → 凭据明文落库(违反约定 8);
  另存一份未脱敏 `output` → 同样是明文落库;把 `output` 从条件变量集合去掉 →
  破坏 `compiler/conditionenv.go` 的唯一定义(违反约定 13)。
  **残余边界**(两处):循环上限的首次求值、`switchAgent` 每轮回边选择 ——
  要彻底消除只能把原文留在盘上或取消 `output` 作为条件变量,属于三个硬约束
  真正互斥的角落。**规避建议**:用 `decision` / `status`(结构化键,原样保留)。
- **`extra_args` 的凭据回写按参数名对齐合并**(第十轮新增,`#224` / `#235`):
  `extra_args` 里的凭据在 GET 时掩码为 `***`(约定 8),而 PUT 回来的 `***`
  **必须被还原成库里的真值**,否则用户改一个无关字段就把真实 API Key 覆盖成
  字面量 `***`(之后每次调用带 `--api-key ***` → 鉴权失败,而用户看到"已保存")。
  **对齐依据必须是参数名,不是下标** —— 增删一个参数后下标全部错位 → A 的凭据
  被写到 B 的**参数名**上 → 凭据泄漏到第三方服务。同源归一
  `--api-key` / `--api_key` / `--API-Key` 视为同一个参数。
  **不要改成下标对齐** —— 那是在"另一种方式"制造同一个泄漏。
- **掩码的判据是"参数名 ∪ 值形态"双判定**(第十五轮新增,`#265`):
  `extra_args` 的掩码此前**只认参数名** → 名字不敏感的选项里藏着凭据时
  (`--header "Authorization: Bearer ghp_xxx"`、`--foo sk-ant-xxx`)掩码**完全
  看不见** → GET 响应里**明文**。这与 #255(`behavior` 只关了"按名"那一半)是
  同一族:**规则齐了,调用点没接上**。
  **现在的口径**:判据是**参数名 ∪ 值形态** —— 参数名指向凭据的,值一律掩;
  名字不敏感但**值本身呈凭据形态**的,同样掩;形态规则**只有 `logx` 一份**
  (第十二轮已收敛,见上面"值的形态规则只有一份定义")。
  **三个连带口径**(改任一处必须同步另两处,约定 13 的同源精神):
  ① **掩码 / 合并 / 剔除共用同一个判定函数** —— 掩码认得而合并不认,
  "按形态被掩的 `***`"回传时找不到原值 → 凭据被丢弃(Agent 每次调用都不带
  鉴权参数,而用户只看到"已保存");
  ② **判定对象是整个参数值**,不是就地替换子串 —— 全仓的 `***` 只表示
  "这个值被掩了,回写时沿用已存值";半掩半明的值无法判断"这一段是不是掩码",
  就地替换还会改写用户自己的原文;
  ③ **布尔开关与负数不是值** —— `--api-key --verbose` 里的 `--verbose` 是
  另一个选项(不带值),`-5` 常是 `--offset` 的值。
  **不要把形态判定再写一份到 `agent` 侧** —— 那是 #246 / #263 同族的漂移。
- **取消以库内的状态为准,不以进程内的句柄为准**(第十五轮新增,`#264` / `#268`):
  `Engine.Cancel` 的"运行中"快路径此前**只看句柄是否存在**。而终态是**先写库**
  的,句柄由执行协程的 `defer` 摘除 —— 两者之间有 ≈**210µs** 的窗口,
  窗口内取消一个**已经完成**的执行会走快路径 → API 回 200"已取消",而执行
  **早已 COMPLETED**(实测:紧密轮询 40/40 命中,修前 40/40 假成功)。
  **现在的口径**:取消也**先读库里的状态**(约定 4 的唯一裁决来源)——
  终态 → `INVALID_TRANSITION`(400);运行中 → 照旧;不存在 → `NOT_FOUND`(404)。
  **配套的一条**:取消**先到**、协程**后启动**时,协程**启动即核对**库里的状态,
  已是 `CANCELLED` 就立刻收尾 —— 否则库里写着"已取消",副作用却已经发生
  (约定 14 同族的"状态与事实不符")。
  **不要把判据改回"句柄在不在"** —— 那不是性能优化,那是 200 假成功。
  **也不要以为"取消应该是幂等的"** —— 约定 6 的幂等 200 只适用于**删除资源**,
  不适用于状态迁移:取消一个已经结束的执行是"取消失败",必须让调用方知道。
- **决策路由只认边上的条件**(轮次 47 新增,`#169`):
  条件写在**边**上,不在节点的 `config.expression` 里。该节点键已废弃
  (降级为警告),前端死输入框已删。**不要**把它"修回"必填 ——
  运行期从不读它,要求用户填一个没有作用的字段是纯粹的伤害。

## 五、on_failure 错误分支(候选设计稿,迭代 36 起草 —— **未立项**)

> 来源:迭代 36 调研 n8n(on-error: continue / continue-using-error-output)、
> Argo(onExit handler)时的最大未落地项。当时判定"触及路由语义与约定 14
> 的最深处,需要独立的语义设计轮"——本节就是那份设计稿,给下一轮立项用。
> **状态:只有设计,没有代码**;立项前先重读本节并复核每条与既有约定的交互。

### 5.1 目标语义

节点失败(重试耗尽后)不立即中止执行,而是沿作者**显式声明**的失败分支继续,
失败原因照常进失败台账与事件流。核心原则:**失败仍然可见**(节点照常落
FAILED),只是"失败之后去哪"由作者决定 —— 这与约定 14(该失败却成功)不冲突:
静默成功是"失败被抹掉",这里是"失败被如实记录 + 显式接管"。

### 5.2 DSL 形状(候选)

```yaml
edges:
  - from: build
    to: notify
    on_failure: true     # 仅当 build 失败(重试耗尽)时走这条边
  - from: build
    to: test             # 无标记:仅成功/WAIT 恢复路径走
```

选边级标记而不是节点级 `on_error: goto` 的理由:失败目的地天然是**图的
结构**(与条件边同层),节点级字符串目标会引入第二套"按名字跳转"的机制
(需求 §36 禁止字符串匹配的精神)。

### 5.3 与既有约定的交互(逐条)

| 约定 | 交互 | 设计回应 |
| --- | --- | --- |
| 约定 14(该失败却成功) | 走失败分支后执行可 COMPLETED —— 这是否算"失败被成功掩盖"? | 不算,但必须**可观测**:执行详情要能看到"经失败分支完成"(如 `workflow.completed` 事件带 `via_failure_branch: [nodeIDs]`);实现期把这个字段加进导出与监控页 |
| 约定 14 的"未执行可达节点必须显式失败" | 失败分支上的节点在无失败时**合法地不执行** | 可达性判定要区分"普通可达"与"仅失败可达":编译期给每个节点标 `failure_only`;收尾检查对 failure_only 节点只在"发生过失败且未走它"时告警 |
| 约定 13(校验/运行同源) | 失败分支的可用变量 | 失败分支里的节点读到的 `status`/`output` 就是失败节点的 —— 无需新变量;`{{variables._error}}` 类的东西**不引入**(错误原因已经在上游 output/事件里) |
| 约定 4(CAS) | 无新状态机状态:节点仍 FAILED,执行仍走既有状态机 | 无改动 |
| 循环保护 | 失败分支可能构成回边 | 复用 loopGuard 计数;校验期把"含 on_failure 边的环"也计入 CYCLE_WITHOUT_CONDITION 检查 |
| 并行区 | 分支内失败走 on_failure 会与失败级联/失败台账打架 | **V1 禁止**:校验期拒绝并行体内的 on_failure 边(`ON_FAILURE_IN_PARALLEL`);先在顺序上下文落地,再评估并行 |
| retry | 先重试,耗尽后才评估失败分支 | withNodeRetries 返回 FAILED 且节点有 on_failure 边 → 路由接管;`node.retry` 事件序列不变 |

### 5.4 校验规则清单(草案)

- `ON_FAILURE_MULTIPLE`:同一节点多条 on_failure 边(暂只允许一条);
- `ON_FAILURE_SELF`:指向自身;`ON_FAILURE_IN_PARALLEL`:并行体内;
- on_failure 边**不允许带 condition**(两个条件语义打架);
- condition 节点的 on_failure 边:无意义,警告;
- 编译期:有 on_failure 边的节点若同时是 merge/human……(逐节点类型过一遍
  与 nodeconfig 契约表同款的探针)。

### 5.5 工作量预估与切分

- 后端:DSL 字段 + 校验(上面清单)+ 编译器 route 接管 + 收尾可达性判定
  扩展 + 回归(runtime/compiler/validator 三层)≈ 1 个迭代的主干;
- 前端:连线属性面板加 on_failure 开关 + 监控页 via_failure_branch 展示 ≈
  半个迭代;
- 冒烟:smoke.sh 加"失败分支接管"一项。

## 四、收官判断(第三十轮 / 迭代 34)—— 还剩什么、值不值得做

> **这一节是前两节的"结论"**。第一、二节列的是**候选方向**;
> 这一节回答的是:**三十三轮做完之后,这些方向还剩多少价值?排序如何?**
>
> **判断的三条依据**:
> ① **三十三轮已经补上了什么底子** —— 缺什么底子的方向现在做代价高,
>    底子已经打好,方向现在做代价低;
> ② **还有几条真缺陷没修** —— 没修完的地方,先修完比加新功能值;
> ③ **改动会碰到哪几条硬性约定** —— 碰的约定越多,回归风险越大。
>
> **一句话结论**:**当前**不值得启动任何一项**大版本迁移**(会话持久化 /
> ADK v2 / 服务器模式统一)。**值得做**的只有三件小事,全部是
> **三十三轮自己留下的尾巴**,且都在**小改动 + 有守卫**的范围内。

### 4.1 三项暂缓决策 —— 判断维持,理由升级

| 方向 | 判断 | 三十三轮之后,理由**变强**还是**变弱** |
| --- | --- | --- |
| **会话持久化**(`session/database`) | **仍然暂缓** | **理由变强**。恢复链路这三十三轮被修得**很稳**:`state_json` 按键分类脱敏(结构化键原样保留)/ 路由决策记进结构化键并**回放**(#205 / #222)/ `task` 与 `variables` **刻意明文保真**(它们是恢复输入,#285)/ 空上下文槽位**可见告警**(#280)/ CAS 是唯一裁决来源(约定 4)/ 失败台账让并行分支的错误不再丢(#250)。**换句话说:这三十三轮把"自己造的那套会话快照"越修越像样** —— ADK 的 `database.NewSessionService` 能替代的是**会话历史查询**这一项收益,而**不是**"恢复可靠性"。收益没变,底子变好了 → **更不着急**:真要迁,现在迁比早迁**更安全**(要重做的语义已经收敛成明确的几条),但收益仍然是"历史查询",不紧急 |
| **ADK v2 升级** | **仍然暂缓,但建议**先做一次**小范围可行性验证** | **理由基本不变,但门槛降了**。v2 提供的 Graph Workflows(`NewFunctionNode` / `NewJoinNode` / `Chain` / `StringRoute`)与 HITL `RequestInput` 节点,和本项目自研的 `routeAgent` / `loopGuard` / WAIT_USER 状态机**一一对应** —— 三十三轮把 WAIT_USER 语义、并行分支错误传播、取消终态、失败台账都理顺了(约定 4 / 13 / 14),**这些正是迁移时最容易出错的部分**,现在它们有**明确的语义 + 回归锁**,迁移的**验收标准可以写出来**。**建议**:不启动迁移,但**用半天做一次可行性验证** —— 拿本仓库**一个**最简单的两节点工作流,在 v2 上跑通"图节点 + RequestInput + 结构化决策" → 如果 v2 的节点语义与本项目的 `decision` / `status` 能对上,再立项;对不上,**这条就彻底关掉**,省下以后反复评估 |
| **服务器模式统一到官方 `-tags server`** | **仍然暂缓** | **理由变强**。自研 REST + SSE 已经不是"胶水",而是**已被外部依赖的对外契约**:`docs/api.md` 逐条写明、两个冒烟脚本逐项断言、桌面模式经 `AssetHandler` 挂载到同一段代码(约定 10)、前端 `api.ts` 的**双分支**被 vitest 契约测试钉住(#257)。三十三轮又给它加了一层:**统一错误体形状** `{error, code, kind}` + **状态码语义表** + **panic 兜底**(#331 / #334)。**换掉它 = 换掉一份已经被测到"逐条可查"的契约**,收益(少一层前端胶水)远小于代价。**除非**真的要做容器部署,否则**不要动** |

### 4.2 值得做的三件小事(全部是三十三轮自己的尾巴)

按**性价比**排序 —— 这三件都是**小改动 + 有现成守卫**的:

| 序 | 事项 | 为什么现在做 | 代价 | 守卫 |
| --- | --- | --- | --- | --- |
| **1** | **把门禁自检改成注册表**(#325) | 门禁自检已经 **41 条**,每条都要在 `scripts/verify.sh` 里**手写一行**;**"删掉一条自检并把计数改小" → 门禁绿**这个方向**不对称**的缺口还在。它是三十三轮里**唯一一个"门禁会绿但门禁变弱"**的已知口子 | 中(改 `scripts/verify.sh` 的自检段,不碰产品代码) | 新增一条"删掉自检 → 门禁红"的自检(**用注册表派生计数**);改完旧的 41 条自检**必须全部还在** |
| **2** | **列表接口的 `limit` 截断加标记**(第 4 条) | `limit > 1000` **静默截断**、响应里**没有**"已截断"标记 —— 用户会以为看到的就是全部。加一个 `truncated: true` 就能消除这个误会 | 小(后端一个字段 + 前端一个可选展示) | 现有 `api/server_test.go:1609` 的溢出用例加一条"响应带 `truncated`" |
| **3** | **`permissions:` 段层级错放的节点级残余**(第 7 条) | DSL 层已经报 `DSL_MISPLACED_KEY`,但**节点 `config` 里的 `permissions` 段**不在应用层顶层键严格化的检查面上 → 两条入口不给出同一个 code(约定 13) | 中(把"归属判定"收敛到一处) | `workflow/dsl/schema_test.go` + `app/application/workflow_payload.go` 的既有探针 |

> **为什么不把它们排在"大方向"前面**:它们**改动小、有现成守卫、且修的是
> 三十三轮自己发现的偏差**;而三项大方向**改动大、要动已被测住的契约、
> 收益是"更好"而不是"更对"**。

### 4.3 明确**不做**的(省下以后反复评估)

| 不做 | 理由 |
| --- | --- |
| **扩大高熵脱敏门槛**(去掉"必须含数字") | 会把 32 字符以上的混合大小写长串(URL、常量名、base64 测试夹具)一并抹掉 —— **毁掉 diff 的审计价值**。实测残余豁免率只有 **0.016%(std)/ 0.092%(raw)**,收益远小于代价(#247 / #78 的取舍) |
