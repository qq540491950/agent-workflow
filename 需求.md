# AI Agent Workflow Orchestrator

你现在需要负责从零开发一个**可配置、可视化、可扩展的多 Agent 工作流编排桌面应用**。

这是一个长期演进的软件项目，不是一次性的 Demo。

必须优先考虑：

* 架构清晰
* 模块解耦
* 可扩展
* 可测试
* 可恢复
* 配置驱动
* Agent 与 Workflow 解耦
* UI 与后端解耦
* 避免硬编码业务流程

---

# 一、项目目标

开发一个桌面端 AI Agent Workflow Orchestrator。

用户可以通过 UI 创建和编辑 Workflow，然后由 Workflow Runtime 自动协调不同的 Agent、Skill、Git 操作和人工操作。

典型流程：

```text
用户输入任务
      │
      ▼
Claude Code：分析 / 制定方案
      │
      ▼
Pi Agent：执行代码修改
      │
      ▼
Claude Code：Review
      │
      ├──────────── APPROVED ────────────┐
      │                                  │
      │                                  ▼
      │                             Pi Agent Submit
      │                                  │
      │                                  ▼
      │                             Claude Code
      │                             下一步判断
      │                                  │
      │                         ┌────────┴────────┐
      │                         ▼                 ▼
      │                       CONTINUE          DONE
      │                         │                 │
      │                         ▼                 ▼
      │                     下一轮任务          Workflow结束
      │
      └──────────── REJECTED ────────────┐
                                         │
                                         ▼
                                   Pi Agent Fix
                                         │
                                         ▼
                                  Claude Code Review
                                         │
                                         └── 循环
```

但以上流程**绝对不能硬编码成一个固定函数**。

最终必须支持用户自己配置类似：

```text
Plan
 ↓
Execute
 ↓
Review
 ├── APPROVED → Submit
 ├── REJECTED → Fix → Review
 └── WAIT_USER → Human Input
```

以及：

```text
Agent A
 ↓
Parallel
 ├── Security Review
 ├── Code Review
 └── Test
 ↓
Merge Result
 ↓
Decision
```

# 五、ADK 的定位

必须理解并遵守下面这个原则：

> ADK Workflow 是 Workflow Runtime，不是本项目的业务 Agent。

Claude Code 和 Pi Agent 是外部 Agent。

例如：

```text
ADK Workflow
      │
      ▼
ClaudeCodeNode
      │
      ▼
ClaudeCodeAdapter
      │
      ▼
claude CLI / RPC
      │
      ▼
Claude Model
```

以及：

```text
ADK Workflow
      │
      ▼
PiAgentNode
      │
      ▼
PiAgentAdapter
      │
      ▼
pi-agent CLI / RPC
      │
      ▼
Pi Model
```

因此：

**不要为了执行 Claude Code 而给 ADK Workflow 配置一个 LLM。**

ADK 自己的 LLM Agent 能力可以作为未来扩展，例如：

```text
Workflow Planner
Decision Agent
Summarizer
```

但不是本系统执行 Claude Code / Pi Agent 的必要条件。

# 十二、Workflow DSL

Workflow 必须配置驱动。

设计 YAML / JSON DSL。

例如：

```yaml
version: "1"

workflow:
  id: coding-task
  name: Coding Task

variables:
  max_review_iterations: 5

nodes:

  - id: plan
    type: agent
    agent: claude-code
    mode: plan

  - id: execute
    type: agent
    agent: pi-agent
    mode: execute

  - id: review
    type: agent
    agent: claude-code
    mode: review

  - id: fix
    type: agent
    agent: pi-agent
    mode: fix

  - id: submit
    type: skill
    agent: pi-agent
    skill: submit

edges:

  - from: plan
    to: execute

  - from: execute
    to: review

  - from: review
    condition: decision == "APPROVED"
    to: submit

  - from: review
    condition: decision == "REJECTED"
    to: fix

  - from: fix
    to: review
```

这个 DSL 只是示例。

需要设计正式 Schema。

这是系统最重要的模块之一。

流程：

```text

Semantic Validation
```

应该：


这样以后更换 Workflow Runtime 时，业务模型不需要重写。

# 十四、Graph Workflow 与 Dynamic Workflow

合理使用 ADK 的两种能力。

稳定结构：

```text
Plan
 ↓
Execute
 ↓
Review
```

使用 Graph。

动态结构：

```text
Review
 ↓
根据 Decision 决定：

APPROVED → Submit

REJECTED → Fix → Review

WAIT_USER → Human

ERROR → Retry
```

使用 Dynamic Workflow。

不要为了使用 Dynamic Workflow 而所有流程都动态化。

原则：

> 静态结构用 Graph，运行时决策使用 Dynamic Workflow。

# 十五、Review → Fix 循环

```text

 ↓

 ↓

 ↓
```


同时需要检测：


```text

```

# 四十二、禁止事项

禁止：

1. 把 Claude Code 和 Pi Agent 的调用逻辑写死在 Workflow Engine。

3. 让 Pi Agent 直接调用 Claude Code。
4. 用字符串匹配判断 Agent Decision。
5. 把整个项目源码无脑塞给 Agent。
6. 把 API Key 写入 Workflow。
7. 把 Workflow 直接绑定到某个 LLM。
8. 把 UI 状态作为后端 Workflow 状态。
9. 把所有状态放在内存。
10. 为了 Demo 绕过权限系统。
11. 使用大量全局变量。
12. 使用巨型 Service。
13. 把业务逻辑全部写在 Wails Binding 中。
14. 自己重新实现 ADK 已经提供的 Workflow Runtime 能力。
15. 使用假实现冒充 ADK 能力。

# 四十九、最终目标

最终这个软件不是一个：

> “Claude Code + Pi Agent 脚本启动器”。

而应该成为：

> **一个通用的、本地优先的、可视化的、多 Agent Workflow Orchestrator。**

未来用户可以通过 UI 定义：

```text
什么时候调用谁
调用什么 Skill
传递什么 Context
如何判断结果
失败怎么办
是否重试
是否循环
是否并行
什么时候暂停等待用户
什么时候提交 Git
什么时候结束
```

并且：

```text
Workflow 本身不关心 Agent 使用什么 LLM。
Agent 本身不关心 Workflow 如何编排。
UI 不关心 ADK 内部实现。
ADK 不承担产品业务模型。
```

最终形成：

```text
                 Workflow
                    │
             ┌──────┴──────┐
             ▼             ▼
          Agent           Skill
             │
      ┌──────┼──────┐
      ▼      ▼      ▼
   Claude    Pi    Codex
      │      │      │
      ▼      ▼      ▼
     各自使用自己的 Model
```

这就是本项目必须保持的核心架构边界。
