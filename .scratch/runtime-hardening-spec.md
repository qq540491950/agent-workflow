# Spec：执行可信性与规模治理（Execution Trust & Scale Hardening）

> 状态：待确认 / 未发布
> 范围：在现有“单机、单执行、短历史”能力之上，补齐并发安全、失败语义、服务边界与规模运营能力；分为六个可独立交付的阶段。
> 原则：不重写运行时；所有新增能力默认向后兼容；每个阶段独立提交、独立回归、独立可回滚。

## Problem Statement

当前项目在单用户、单执行、短历史的演示场景下表现很好，但一旦进入真实使用，用户会遇到一组彼此关联的问题：

1. **并发执行会互相踩踏工作区。** 所有执行共享同一个 Git 工作目录；默认并发不设上限。两个编码工作流同时运行时，会同时对同一棵工作树执行 checkout、改文件、`git add -A` 和 commit，A 的提交可能带上 B 的修改，review 也可能看到另一条执行改到一半的文件。
2. **失败之后没有编排出口。** 节点失败（重试耗尽）后执行直接终止，只能手动重试或跳过。用户无法声明“失败后通知 / 回滚 / 走修复分支”，这使大量真实工作流只能在失败后人工介入。
3. **服务模式的信任边界没有闭合。** 监听地址可通过 `--addr :8080` 等方式暴露到所有网卡；API 无鉴权、无 Origin/Host 校验、不检查 Content-Type；浏览器页面可以向本机服务发起不触发预检的写请求。一个本机调试口可以在用户不知情时变成可被网页或局域网调用的控制面。
4. **执行与事件的历史规模没有运营化。** 执行列表默认返回全量，并逐行解析完整的工作流快照与会话状态；单次执行的事件接口没有分页/游标，监控页每次刷新全量重拉；事件表无保留策略。历史越长，列表、监控和执行写入互相拖慢。
5. **并发没有全局背压。** 只有“每工作流”的 fail-fast 上限，没有全局并发上限、排队、公平调度或优先级。server 模式或脚本客户端可以瞬间启动大量执行，每个执行再派生多个 CLI 子进程。
6. **可观测性不足。** 有事件审计和内部计数器，但没有指标、链路追踪、token/成本统计，也没有能反映数据库状态与队列深度的健康检查。用户无法回答“哪个节点最慢”“失败率多少”“这次执行花了多少 token”。

这些问题的共同点是：内部正确性已经很强，但系统还缺少“在并发、失败、长历史和不可信调用方下仍然可信”的运行边界。

## Solution

分六个阶段交付，每个阶段都可以单独上线、单独验证：

- **阶段 A：服务模式信任边界。** 默认只监听回环；非回环必须显式开启并携带令牌；校验 Origin / Host / Content-Type；补齐 HTTP 超时。
- **阶段 B：执行级工作区租约。** 同一个工作目录在同一时刻只允许一个执行持有；等待人工时释放，恢复时重新获取；冲突时明确拒绝或排队。
- **阶段 C：失败分支（`on_failure`）。** 允许作者声明“节点失败后走哪条边”；失败节点仍为 FAILED，但执行可以经失败分支完成，并在执行详情、事件、导出中显式标注。
- **阶段 D：全局并发与队列。** 增加全局并发上限、`QUEUED` 状态、公平调度、队列取消与重启恢复；默认关闭排队以保持既有 `WORKFLOW_BUSY` 契约。
- **阶段 E：历史与事件规模。** 执行列表改为摘要 DTO + 游标分页；事件接口增加 `after_seq` / `before_seq`；监控页增量追加；补索引、只读连接池、保留策略与性能基准。
- **阶段 F：可观测性与成本。** 运行时统计端点、OTel span、健康检查纳入数据库状态、Agent token 用量与执行级聚合。

阶段 B 与阶段 D 有依赖关系：工作区冲突在未开启排队时返回 `WORKSPACE_BUSY`，开启排队后进入 `QUEUED`。阶段 C 与阶段 D 可以并行开发，但都依赖阶段 A 的错误码/中间件基础设施保持稳定。

## User Stories

### 服务模式信任边界

1. 作为本机用户，我希望服务器默认只监听回环地址，以免我按常见习惯写成 `:8080` 时把 API 暴露到局域网。
2. 作为远程使用者，我希望必须显式开启远程访问并提供令牌，以免任何人打开一个网页就能操作我的执行。
3. 作为安全负责人，我希望来自非白名单 Origin 的写请求被拒绝，以免浏览器页面借我的本机服务发起 CSRF。
4. 作为运维人员，我希望 Host 头必须匹配受信地址，以免 DNS rebinding 让恶意页面读取本机 API 的响应。
5. 作为运维人员，我希望 JSON 写接口要求正确的 Content-Type，以免简单请求绕过浏览器的预检。
6. 作为运维人员，我希望 HTTP 服务器有读头超时和空闲超时，以免慢连接长期占用资源。
7. 作为 API 客户端，我希望未授权、来源非法、媒体类型不支持分别返回 401 / 403 / 415，并能拿到稳定的错误码。
8. 作为桌面用户，我希望桌面模式完全不受服务器模式鉴权改动影响。

### 执行级工作区租约

9. 作为工作流作者，我希望同一个工作目录上的执行串行化，以免两个编码任务互相覆盖文件。
10. 作为用户，我希望工作区被占用时得到明确提示（`WORKSPACE_BUSY`）或进入队列，而不是静默冲突。
11. 作为用户，我希望等待人工审批的执行释放工作区，以免一个长期挂起的审批阻塞其他人。
12. 作为用户，我希望提交人工输入后重新获取工作区；如果已被占用，应明确告诉我而不是继续执行。
13. 作为审计者，我希望执行记录里能看到这次执行使用了哪些工作区目录。
14. 作为工作流作者，我希望多个节点使用不同 `working_dir` 时，租约覆盖所有实际目录，而不是只锁一个。
15. 作为用户，我希望取消执行时立即释放工作区租约。
16. 作为维护者，我希望租约只存在于进程内，不引入新的持久化状态；崩溃后的执行仍按既有恢复逻辑处理。

### 失败分支（`on_failure`）

17. 作为工作流作者，我希望在边上声明 `on_failure: true`，让节点重试耗尽后走通知、回滚或修复分支。
18. 作为工作流作者，我希望失败分支只在重试耗尽后触发，顺序确定，不会和重试竞争。
19. 作为用户，我希望失败节点仍然显示 FAILED，不被失败分支“洗白”成成功。
20. 作为用户，我希望执行详情明确标注“经失败分支完成”，并能看到是哪些节点走了失败分支。
21. 作为审计者，我希望 `workflow.completed` 事件和导出记录都包含 `via_failure_branch`。
22. 作为工作流作者，我希望校验期拒绝同一节点多条失败边、自环、带条件的失败边，以及并行区内的失败边。
23. 作为工作流作者，我希望失败边形成的环被循环守卫拒绝，除非有明确的条件出口。
24. 作为用户，我希望失败分支里可以继续使用 human / agent / script / git 节点，并保持既有权限与脱敏语义。
25. 作为用户，我希望恢复一个停在失败分支里的执行时，路由选择被回放，不会换到另一条边。
26. 作为用户，我希望失败分支本身失败时，执行最终为 FAILED，并能同时看到原始失败与分支失败的原因。
27. 作为工作流作者，我希望没有失败边时，现有“失败即终止”的行为逐位不变。
28. 作为设计器用户，我希望在连线属性面板里开关失败边，并在画布上能区分普通边与失败边。

### 全局并发与队列

29. 作为运维人员，我希望设置全局最大活跃执行数，以免一次启动太多 CLI 子进程。
30. 作为用户，我希望超过上限时可以排队并看到队列位置，而不是只能反复点击重试。
31. 作为用户，我希望排队按公平顺序调度，避免一个大批量工作流长期饿死其他工作流。
32. 作为用户，我希望取消排队中的执行时，它不再被调度，并发出明确的取消事件。
33. 作为运维人员，我希望重启后排队中的执行能恢复，不丢失已经接受的请求。
34. 作为 API 客户端，我希望开启排队时启动返回 202 + `QUEUED`，关闭排队时保持既有 `WORKFLOW_BUSY` 409。
35. 作为用户，我希望前端显示 `QUEUED` 徽标、队列位置和“取消排队”操作。
36. 作为运维人员，我希望队列有长度上限，满时返回明确错误，而不是无限占用内存。
37. 作为用户，我希望每工作流并发上限与全局并发上限同时生效，且不会因为一个上限被绕过另一个。
38. 作为维护者，我希望 `QUEUED` 是持久化状态，状态迁移仍全部走 CAS。

### 历史与事件规模

39. 作为用户，我希望执行列表只返回摘要字段并默认分页，历史积累后仍然快速打开。
40. 作为 API 客户端，我希望用游标翻页，避免 offset 分页在并发写入时漂移。
41. 作为用户，我希望监控页在收到新事件时增量追加，而不是每 200ms 重拉全部事件。
42. 作为用户，我希望事件很多时仍能看到最近记录，并能通过导出查看完整审计记录。
43. 作为用户，我希望能够加载更早的事件，而不是只能看最近一屏。
44. 作为运维人员，我希望配置事件/执行的保留期，或手动触发清理，控制数据库增长。
45. 作为运维人员，我希望清理前有明确的 dry-run/统计，避免误删审计数据。
46. 作为开发者，我希望执行/事件查询有复合索引和只读连接池，读请求不再和同步事件写入抢同一条连接。
47. 作为开发者，我希望有覆盖 1 万执行 / 100 万事件的性能基准，防止历史规模回归。
48. 作为用户，我希望列表接口的截断/分页行为有明确响应头，客户端能区分“到底了”和“还有更多”。

### 可观测性与成本

49. 作为运维人员，我希望看到运行中、排队中、成功、失败、取消、事件落库失败、状态提交失败的计数。
50. 作为运维人员，我希望看到执行/节点耗时、队列等待时间、数据库延迟和 SSE 订阅数。
51. 作为开发者，我希望每个执行、节点和 Agent 调用都有 OTel span，并能通过环境变量接入现有追踪系统。
52. 作为用户，我希望在节点和执行详情里看到 token 用量（输入/输出/总计）。
53. 作为审计者，我希望用量数据进入导出记录，且不包含凭据。
54. 作为运维人员，我希望健康检查在数据库不可用时返回非 200，而不是永远 `{"status":"ok"}`。
55. 作为维护者，我希望未配置 OTEL 时追踪是零开销的 no-op，不影响桌面模式。

### 跨阶段

56. 作为用户，我希望升级后现有工作流、API 客户端和桌面模式行为保持不变，除非我显式开启新设置。
57. 作为开发者，我希望所有新增错误码都有前端中文提示，错误码全集守卫保持绿色。
58. 作为维护者，我希望每个阶段都有红→绿回归、`-race` 测试和迁移兼容测试。
59. 作为维护者，我希望新增的 DSL 字段、API 字段和数据库列都有文档记录和对外契约说明。

## Implementation Decisions

### 通用约定

- 所有新增能力默认向后兼容：DSL 只做增量字段；API 只做增量参数/响应头；数据库只做可空列增量迁移；既有错误码语义不变。
- 新增状态、路由、错误码都必须遵守现有约定：状态迁移走 CAS；该失败却成功视为 P0；校验期与运行期同源；共享可变状态加锁。
- 每个阶段独立提交；回归测试与实现同 commit；`gofmt -l` 为空；门禁九步全绿。
- 不引入大版本迁移（ADK v2、会话持久化、服务器模式统一）作为本 spec 的前置条件。

### 阶段 A：服务模式信任边界

**启动参数与监听**

- 新增 `--allow-remote`：允许非回环监听；未开启时，任何非回环地址（包括空 host、`0.0.0.0`、局域网 IP）在启动时直接报错退出。
- 空 host（`:8080`）一律视为“所有网卡”，必须同时提供 `--allow-remote` 与显式 host；推荐直接拒绝空 host，要求写成 `0.0.0.0:8080`。
- 新增 `--auth-token`：远程模式可用；未提供时启动生成一次性随机 token，打印到 stderr，进程内只保留摘要/常量时间比较用的值，不写日志、不进 SQLite。
- 远程模式下所有 `/api/*`（`/api/health` 可豁免）要求 `Authorization: Bearer <token>`；token 不得通过 query 参数传递。

**请求边界**

- 新增 HTTP 中间件：校验 `Host`、`Origin`、`Content-Type`。
- 回环模式：只允许受信 Host（`127.0.0.1:<port>`、`localhost:<port>`、`[::1]:<port>`）；带 `Origin` 的请求必须与受信源完全匹配；无 `Origin` 的本机客户端（CLI）放行。
- 远程模式：Host 必须匹配配置的监听地址；Origin 必须匹配同源 SPA 或显式配置的白名单；其他跨源请求返回 403。
- 写方法（POST/PUT/PATCH/DELETE）要求 `application/json`；工作流导入允许 `application/yaml` / `text/yaml`；不匹配返回 415。
- 错误码：`UNAUTHORIZED`（401）、`FORBIDDEN_ORIGIN`（403）、`UNSUPPORTED_MEDIA_TYPE`（415）；前端错误码表同步。
- 不添加 CORS 响应头；跨源客户端不应依赖浏览器读取响应。若未来需要，单独设计 CORS 白名单。

**HTTP 服务器**

- 设置 `ReadHeaderTimeout`（建议 10s）、`ReadTimeout`（建议 30s）、`IdleTimeout`（建议 120s）。
- 不设置全局 `WriteTimeout`，避免掐断 SSE；SSE 继续使用每连接写超时；JSON 处理器可通过响应控制器设置单次写超时。
- 优雅关闭逻辑保持现状，关闭超时与执行收尾逻辑不变。

**文档与测试**

- README、API 文档明确“默认仅回环；远程必须显式开启并带 token”。
- 冒烟脚本继续使用回环，不需要 token；新增远程模式负路径冒烟（无 token 401、错误 Origin 403、错误 Content-Type 415）。
- 桌面模式不经过这些中间件，行为不变。

### 阶段 B：执行级工作区租约

**领域模型**

- `Execution` 新增 `workspace_dirs`（JSON 字符串数组，规范化绝对路径，去重排序）；用于审计与 UI 展示。
- 不新增持久化租约表。租约是进程内资源，进程重启后由执行恢复逻辑统一处理。

**租约管理器**

- 新增 `WorkspaceLeaseManager` 接口，注入运行时引擎：
  - `Acquire(ctx, executionID, dirs) (Lease, error)`
  - `Lease.Release()`
- 默认实现是进程内引用计数 + 互斥：按目录规范化路径加锁；多个目录按字典序依次获取，避免死锁；任一目录被占用时返回可识别的 `WORKSPACE_BUSY`。
- 测试可实现确定性 fake；生产实现不依赖数据库。

**目录解析**

- 从执行快照收集所有可能产生副作用的节点目录：agent / script / git 节点的 `working_dir`，加上全局 Git 工作目录。
- 目录为空或相对路径时按现有语义解析（相对当前进程目录）；规范化后去重排序。
- 如果某个节点在运行期才决定目录（目前 DSL 不支持模板化 `working_dir`），该阶段按“无法预知则不租约”处理；未来若支持动态目录，再扩展。

**生命周期**

- `Start`：在插入执行行之前获取租约；获取失败且未开启排队 → 409 `WORKSPACE_BUSY`；开启排队 → 执行进入 `QUEUED`（阶段 D）。
- `Resume` / `RetryNode`：重新获取租约；失败则保持 `WAITING_USER` / `FAILED` 并返回 `WORKSPACE_BUSY`。
- 执行进入 `WAITING_USER` 终态时释放租约；执行终态（COMPLETED / FAILED / CANCELLED）释放租约；`Cancel` 立即释放。
- 释放必须幂等；执行协程的 `defer` 与显式释放不能重复破坏引用计数。
- 工作区租约不改变节点级权限、脱敏和事件语义。

**后续（不在本阶段）**

- 每次执行独立 `git worktree` / 工作区副本、自动清理与合并，属于后续独立 spec；本阶段先消除“同一目录并发写”的数据损坏风险。

### 阶段 C：失败分支（`on_failure`）

**DSL 与模型**

- `Edge` 新增 `OnFailure bool`（YAML/JSON：`on_failure: true`）。
- 失败边与 `condition` 互斥；同一节点最多一条失败边；不允许自环。
- 阶段 C 只允许顺序上下文；并行区内的失败边在校验期直接拒绝。
- 失败边形成的环按“无条件回边”处理，除非环上有明确条件出口；否则校验期拒绝。

**校验规则（新增错误码）**

- `ON_FAILURE_MULTIPLE`：同一节点多条失败边。
- `ON_FAILURE_SELF`：失败边指向自身。
- `ON_FAILURE_WITH_CONDITION`：失败边同时带条件。
- `ON_FAILURE_IN_PARALLEL`：并行区内出现失败边（V1 禁止）。
- `ON_FAILURE_CYCLE`：失败边构成无条件环。
- 失败分支节点的“未执行”不应被当成普通不可达节点报错；收尾可达性判定要区分“普通可达”与“仅失败可达”。

**运行期语义**

- 节点重试耗尽后仍落 FAILED，照常发 `node.failed` 事件与失败台账；此时若存在失败边，不设置全局 abort，而是把路由选择写入结构化状态（键形如 `route:<node>:failure`，值为目标节点 ID），并继续执行失败分支。
- 失败分支上的节点正常执行；它们的状态、输出、权限、脱敏与普通节点一致。
- 失败分支执行完毕后，按正常路由继续；如果失败分支直接结束，执行可以落 COMPLETED，但必须带 `via_failure_branch` 证据。
- 失败分支自身失败：执行落 FAILED；错误信息同时包含原始失败与分支失败原因；不得只保留其中一个。
- 失败节点永远不会被改写为 SUCCESS；执行 COMPLETED 只表示“失败被显式接管”，不表示“没有失败”。
- 恢复：失败分支的路由选择走结构化状态回放；恢复后的执行不得重新求值条件而换道。
- 并行：V1 只在顺序上下文实现；并行区内的失败边校验期拒绝，避免与失败台账/级联取消打架。

**可观测与展示**

- `workflow.completed` 事件 payload 新增 `via_failure_branch`（节点 ID 数组）。
- `Execution` 新增 `via_failure_branch`（JSON 数组，可空）；执行详情、列表摘要、导出都包含它。
- 前端执行详情显示“经失败分支完成”徽标；节点列表里失败节点仍显示 FAILED；导出保留原始失败原因。
- 设计器连线属性面板新增失败边开关；画布用不同线型/颜色区分失败边；校验错误定位到边。

### 阶段 D：全局并发与队列

**状态机**

- 新增 `QUEUED` 执行状态，位于 `CREATED` 与 `RUNNING` 之间。
- 合法迁移：`CREATED → QUEUED`、`QUEUED → RUNNING`、`QUEUED → CANCELLED`、`QUEUED → FAILED`（工作流被删除/禁用等不可执行原因）。
- 所有迁移继续走 CAS；`QUEUED` 行必须有 `queued_at`。
- `CountActiveExecutions` 的口径要明确：`QUEUED` 是否占用每工作流额度由设置决定；默认不占用（排队本身就是为了等待额度）。

**设置**

- `runtime.max_active_executions`：全局最大活跃执行数，0 = 不限；新库默认 4，已有库升级保持 0，避免改变行为。
- `runtime.queue_enabled`：是否在超限时排队；默认 false，保持既有 409 契约。
- `runtime.max_queued_executions`：队列长度上限；默认 100。
- `runtime.queue_policy`：`fifo` | `fair`；默认 `fair`（按工作流轮转）。
- 设置页展示当前运行/排队数与建议值；0 = 不限时给出风险提示。

**启动与调度**

- `Start`：校验入参 → 解析工作区 → 尝试获取租约 → 检查每工作流上限与全局上限。
- 未开启排队：超限返回 409；每工作流仍用 `WORKFLOW_BUSY`，全局用 `SYSTEM_BUSY`（新码）。
- 开启排队：无可用槽位时插入 `QUEUED` 行并返回 202；队列满返回 `QUEUE_FULL`（429 或 409，文档固定一种）。
- 调度器是进程内单协程/工作池：持有运行中集合，按公平策略从队列取执行；取到后 CAS `QUEUED → RUNNING`、获取租约、启动执行协程。
- 执行终态、取消、租约释放都会唤醒调度器；调度器不阻塞 API 请求。
- `Resume` / `RetryNode` 不走队列（它们已有执行行）；但仍需获取工作区租约，并受全局上限约束。
- 关闭：优雅关闭时不再取新执行；`QUEUED` 行保留，下次启动按 `queued_at` 顺序恢复；运行中执行按现有逻辑收尾。

**取消与恢复**

- 取消 `QUEUED`：CAS 到 CANCELLED，发 `workflow.cancelled`，从队列移除；没有执行协程。
- 启动恢复：把 `QUEUED` 行重新入队；如果工作流已删除/禁用/快照损坏，CAS 到 FAILED 并给可读原因。
- 队列中的执行不得产生任何副作用（不获取工作区、不启动 CLI）。

**展示与统计**

- 前端新增 `QUEUED` 状态徽章、队列位置、取消排队按钮；列表过滤包含排队。
- 运行时统计暴露 running / queued / oldest_queued_age / queue_depth / rejected_total。
- 队列事件不新增独立事件类型，复用执行状态变更事件；避免前端事件表膨胀。

### 阶段 E：历史与事件规模

**执行列表**

- 新增执行摘要 DTO：id、workflow_id、workflow_name、workflow_version、state、task（脱敏）、created_at、started_at、finished_at、error（脱敏）、via_failure_branch。不包含 snapshot、state_json、node_states_json。
- 列表查询只 SELECT 摘要列；默认 limit 50，最大 500；`limit=0` 按默认值处理，不再表示“全部”。
- 游标：`created_at + id` 的稳定游标，参数 `cursor`；响应仍为裸数组，附加 `X-Next-Cursor` 头；没有更多时不带该头。
- 保留 `X-Limit-Truncated` / `X-Limit-Applied` 语义用于显式 limit 收敛；游标用于翻页。
- 前端列表页改用游标加载更多；不再一次性拉全量。

**事件接口**

- `GET /api/executions/{id}/events` 支持：
  - 无参数：返回最近 N 条（默认 500，最大 2000），按时间升序；
  - `after_seq=N`：返回 seq > N 的增量，升序；
  - `before_seq=N`：返回 N 之前的一页，升序；
  - `after_seq` 与 `before_seq` 互斥。
- 响应头：`X-Next-Seq`（本次返回的最大 seq）、`X-Has-Older` / `X-Has-Newer`（可选）。
- 监控页：首屏取最近 500 条；SSE 事件到达时直接追加 payload，不再全量重拉；内存上限 2000 条，超出丢弃最旧并提示“仅显示最近 2000 条，完整记录请导出”；提供“加载更早”。
- 执行/节点/制品仍可刷新，但事件不再参与每次全量刷新；节点列表可改为差量或降低刷新频率。

**存储与索引**

- `events` 增加 `(execution_id, seq)` 复合索引；`executions` 增加 `(state, created_at)`、`(workflow_id, created_at)` 复合索引。
- 数据库连接：保留一个写连接；新增只读连接池（WAL 下允许并发读），列表/详情/事件/统计读走只读池，状态 CAS、事件写入、元信息写入走写连接。
- 事件写入仍是同步的（审计契约不变）；使用 prepared statement 降低开销。
- 新增列迁移使用幂等 `ADD COLUMN`（先查 `PRAGMA table_info`），不删除旧列、不重写既有数据；迁移失败必须显式报错。

**保留策略**

- 设置项：`runtime.event_retention_days`、`runtime.execution_retention_days`、`runtime.max_events_per_execution`，默认 0 = 不自动删除。
- 新增维护端点：`POST /api/maintenance/cleanup`，支持 `dry_run=true` 先返回将删除的行数/字节数；正式执行需要显式确认。
- 清理顺序：events → artifacts → execution_nodes → executions；只清理终态执行；不清理 RUNNING / WAITING_USER / QUEUED。
- 清理后可选 `PRAGMA optimize`；VACUUM 作为显式运维操作，不在请求线程里跑。
- 文档说明“备份导出是唯一允许明文凭据的出口”，保留策略不影响该语义。

**性能基准**

- 新增基准/负载脚本：至少 1 万执行、100 万事件；测列表分页、执行详情、事件增量、事件写入的 P95。
- 基准不放进日常门禁（避免机器差异导致假红），作为独立脚本/ nightly 使用；文档记录基线与回归阈值。

### 阶段 F：可观测性与成本

**运行时统计**

- 新增只读端点 `GET /api/runtime/stats`，返回 JSON：
  - running、queued、queue_depth、oldest_queued_age；
  - completed/failed/cancelled 计数；
  - event_persist_failures、state_commit_failures、escalate_expected/unexpected；
  - sse_subscribers；
  - DB ping 延迟（可选 p50/p95，按最近窗口）。
- 数据源复用现有原子计数器 + 调度器/事件总线统计；不引入新的全局可变状态，必要时加锁。

**链路追踪**

- 初始化 OTel tracer provider：仅当配置了 OTLP endpoint 时启用；未配置时 no-op。
- span：`workflow.execution`、`workflow.node`、`agent.call`、`git.operation`、`script.exec`。
- 属性：execution_id、workflow_id、node_id、node_type、agent_id、mode、attempt、status；错误 span 记录状态与脱敏后的错误消息。
- 上下文沿执行 ctx 传播；并行分支各自成 span，父子关系正确。
- 不把 prompt 全文、环境变量、凭据放进 span 属性。

**Token 用量**

- `AgentResponse` 新增可选 `Usage`：input_tokens、output_tokens、total_tokens、model、可选 cost_usd。
- Claude 适配器从 JSON 信封的 usage 字段解析（若存在）；pi 等自由文本适配器可以留空；不得猜测 token 数。
- 节点明细、执行记录持久化用量；执行级聚合；API 详情/导出返回；前端显示。
- 不内置模型价格表；`cost_usd` 仅在 CLI/适配器明确提供时展示；否则只显示 token。

**健康检查**

- `GET /api/health` 增加数据库 ping、running/queued 数；DB 不可用时返回 503 + 结构化错误体。
- 健康检查不要求鉴权（远程模式下也允许），但不得暴露路径、凭据或详细 SQL 错误。

### 兼容性与错误码

- 新增错误码：`UNAUTHORIZED`、`FORBIDDEN_ORIGIN`、`UNSUPPORTED_MEDIA_TYPE`、`WORKSPACE_BUSY`、`SYSTEM_BUSY`、`QUEUE_FULL`、`ON_FAILURE_MULTIPLE`、`ON_FAILURE_SELF`、`ON_FAILURE_WITH_CONDITION`、`ON_FAILURE_IN_PARALLEL`、`ON_FAILURE_CYCLE`。
- 前端错误码全集守卫要求每个后端码都有中文提示；新增码必须同 commit 更新。
- 既有 `WORKFLOW_BUSY`、`INVALID_TRANSITION`、`NOT_FOUND` 等语义保持不变。
- 关闭排队时，启动行为与当前一致；开启排队是显式设置。
- 列表默认 limit 从“全部”改为 50 是唯一有意的破坏性变更，需在 API 文档、README、前端契约测试中明确；第三方客户端应改用游标。

## Testing Decisions

### 好测试的判据

- 只测外部行为：HTTP 响应、执行状态、节点状态、事件流、持久化结果、UI 可见文本；不测私有函数或内部实现细节。
- 优先使用现有 seam；新增 seam 越少越好。
- 不使用 `time.Sleep` 碰运气建立并发窗口；用屏障、通道、确定性 fake 或现有探针。
- 每条修复至少有一个“改坏实现就变红”的回归；安全/队列/租约类用例要有负路径。
- 并发相关用例在 `-race` 下运行；涉及排序的断言按稳定键排序，不依赖调度顺序。

### 测试 seam（按优先级）

1. **Engine 集成 seam（最高，首选）**：使用现有运行时 fixture（临时 SQLite、真实持久层、mock agent、临时 Git 目录），通过 `Start` / `Resume` / `RetryNode` / `Cancel` 驱动。覆盖工作区租约、队列、失败分支、恢复、组件协作。现有 `newFixture` / `newMinimalEngine` / `waitForState` / 事件订阅可作为 prior art。
2. **HTTP API seam**：`httptest` + 真实 `App`（临时数据目录），覆盖鉴权、Origin/Host/Content-Type、分页、事件游标、健康检查、统计端点。现有 API 契约测试与双模式测试是 prior art；真实进程用冒烟脚本补端到端。
3. **前端 seam**：vitest + mock `api` / SSE 订阅，覆盖 QUEUED 徽标、失败分支徽标、事件增量追加、分页加载、错误提示。现有 ExecutionMonitor / WorkflowHistory / api 契约测试是 prior art。
4. **新增注入点（仅两个）**：
   - `WorkspaceLeaseManager`：生产实现 + 确定性 fake；用于并发/释放/重入测试。
   - `Scheduler`（或等价的队列接口）：生产实现 + 可控时钟/手动推进的 fake；用于公平性、取消、重启恢复测试。
   - 除此之外不新增公开 seam；队列/租约的内部实现通过 Engine 集成测试观察。

### 分阶段测试清单

**阶段 A**

- 启动参数：回环默认通过；`--addr :8080` / `0.0.0.0` 未开 `--allow-remote` 启动失败；远程模式无 token 401；错误 token 401；正确 token 200。
- Origin：同源放行；`Origin: https://evil.example` 403；无 Origin 的本机客户端放行；Host 不匹配（DNS rebinding 形态）403。
- Content-Type：JSON 写接口 `text/plain` 415；`application/json` 通过；导入允许 YAML。
- 超时：`httptest` 慢头连接在 `ReadHeaderTimeout` 后断开；SSE 不被全局写超时掐断。
- 桌面模式回归：AssetHandler 路径不经过新中间件，既有 API 测试全绿。
- 冒烟：loopback 无需 token；远程负路径 401/403/415。

**阶段 B**

- 两个执行同目录并发：第二个在未开排队时 `WORKSPACE_BUSY`；第一个结束后第二个可启动。
- WAITING_USER 释放租约：执行等待人工时，另一个同目录执行可以启动；Resume 时如被占用返回 `WORKSPACE_BUSY` 且状态保持。
- 取消/失败/完成都释放租约；重复释放幂等；`-race` 下无竞态。
- 多目录按排序获取；部分目录被占用时整体失败，不留下半持有租约。
- 执行记录包含规范化目录列表；UI 可展示。
- 不改变不同目录执行的并发性。

**阶段 C**

- 成功路径：有失败边但节点成功 → 失败分支不执行，行为与没有失败边一致。
- 失败路径：agent 失败 + 重试耗尽 → 失败节点 FAILED、失败分支执行、执行 COMPLETED + `via_failure_branch`；事件/导出包含证据。
- 重试顺序：重试期间不触发失败分支；最后一次失败后才触发；`node.retry` 序列不变。
- 失败分支自身失败 → 执行 FAILED，错误同时包含原始失败与分支失败。
- 恢复：失败分支中的 human 节点等待 → Resume 继续失败分支；路由不重新求值。
- 校验负路径：多条/自环/带条件/并行区内/无条件环分别报对应错误码；无失败边的存量工作流逐位不变。
- 前端：徽标、连线开关、校验错误定位；列表摘要包含 `via_failure_branch`。

**阶段 D**

- 全局上限：上限 1，两个工作流同时启动 → 第二个 `SYSTEM_BUSY`（排队关闭）或 QUEUED（排队开启）。
- 每工作流上限仍生效；两个上限同时满足才启动。
- 排队：FIFO 与 fair 顺序断言；公平模式下两个工作流交替；取消 QUEUED 后不再调度。
- 重启：QUEUED 行恢复入队；已删除/禁用工作流的 QUEUED 行落 FAILED。
- 队列满：`QUEUE_FULL`，不创建执行行。
- `QUEUED` 不获取工作区、不启动子进程、不产生节点事件。
- 状态机/CAS：并发取消与调度只允许一路成功；`-race`。
- 前端：QUEUED 徽标、位置、取消按钮、过滤。

**阶段 E**

- 列表：默认 50；游标翻页稳定；不返回 snapshot/state；摘要字段完整；脱敏仍生效。
- `limit=0` 按默认处理，不再全量；超上限收敛并带头；没有更多时无 `X-Next-Cursor`。
- 事件：无参数返回最近 N 条升序；`after_seq` 增量；`before_seq` 更早；互斥参数 400；`X-Next-Seq` 正确。
- 监控页：SSE 到达增量追加，不重复拉全量；超过 2000 条丢弃最旧并提示；加载更早可用。
- 索引/只读池：查询计划验证使用复合索引；读请求不阻塞写入（集成/基准）。
- 保留：dry-run 统计准确；正式清理只删终态；保留期 0 不删；清理后列表/详情/导出不报错。
- 基准：1 万执行/100 万事件下 P95 有记录；回归阈值写入测试文档。

**阶段 F**

- `/api/runtime/stats`：字段完整、类型稳定、无敏感信息；并发执行下计数一致。
- OTel：未配置时 no-op；配置内存 exporter 时 execution/node/agent span 的父子关系与属性正确；错误 span 状态正确；不泄漏 prompt/凭据。
- Usage：Claude 信封含 usage → 解析并持久化；不含 usage → 空值不猜测；执行聚合正确；导出包含；前端显示。
- 健康：DB 正常 200；DB 关闭/损坏 503；不泄漏内部细节。
- 计数：事件落库失败、状态提交失败、SSE 订阅数可观测；与既有计数器一致。

### 回归与门禁

- 每个阶段新增测试必须“改坏实现变红”；沿用现有红→绿实测方法。
- 后端跑 `go vet` + `go test -race`；前端跑 `npm run build` + `npx vitest run`；门禁九步全绿。
- 新增/修改 API 时同步前端 API 双分支、契约测试、错误码全集守卫、`docs/api.md`。
- 冒烟脚本增加：远程模式负路径、QUEUED、工作区冲突、失败分支、事件游标（至少各一条正向 + 一条负向）。
- 迁移测试：旧库（无新列/无新索引）启动后自动补列/索引，既有数据可读；新库往返一致。

## Out of Scope

以下能力明确不在本期实施，另立 spec 或在后续迭代评估：

- **动态扇出 / `map` / `foreach`**：按运行期数组并行分发；需要新的 DSL 节点、并发上限、聚合语义与失败台账集成。
- **HITL 超时、升级、指派、结构化表单**：需要新的时间触发机制、通知/升级策略与表单 schema；本期只保留现有 prompt/responses。
- **git / subworkflow 节点的统一重试**：需要先定义副作用幂等与不可重试错误分类；本期只保留 agent/script 重试。
- **cron / webhook / 文件触发**：涉及调度器、持久化 schedule、执行来源与产品决策；本期只做手动/API 启动。
- **Agent token 流式输出**：需要适配器流式协议、增量持久化与 SSE 协议扩展；本期只保留心跳与 execution/node 级刷新。
- **版本 diff / 一键回滚、Designer undo/redo、单节点试跑**：独立 UX 工作，不与运行时边界混做。
- **插件/远程 worker 协议、动态 Agent/Skill 发现**：需要进程隔离、协议、签名与权限模型；本期保持编译期注册。
- **ADK 会话持久化 / 完整 durable execution**：维持 ROADMAP 的暂缓决策；本期只做工作区租约与既有重放恢复。
- **多租户、RBAC、TLS 终止、公网部署加固**：服务模式仍定位为本机/受信网络工具；远程模式只提供 token 与来源校验，不替代反向代理/网关。
- **通用集成节点生态（HTTP/数据库/消息队列/邮件等）**：不把产品做成 n8n；按需另立节点 spec。
- **公开漏洞细节**：本 spec 包含服务模式攻击面，仓库是 public，禁止直接发布到公开 issue；如需跟踪，使用私有安全公告或脱敏后的任务描述。

## Further Notes

### 兼容与发布顺序

1. **阶段 A 先发**：它是纯边界加固，风险最低，且为后续错误码/中间件打底。
2. **阶段 B 与阶段 D 联动**：先实现租约的 fail-fast（`WORKSPACE_BUSY`），再接排队；避免一次性引入两个新状态。
3. **阶段 C 独立**：DSL 增量、校验严格、顺序上下文先行；并行区失败边明确拒绝。
4. **阶段 E 先做列表投影与游标，再做保留清理**：先解决“读得慢”，再解决“存得多”；保留策略默认关闭，避免升级误删。
5. **阶段 F 最后做**：它依赖队列、租约、失败分支的稳定计数口径；先做 JSON 统计与 OTel span，Prometheus exporter 可后续再加。

### 风险与缓解

- **失败分支触及路由语义**：严格按 ROADMAP 的设计稿与校验规则；V1 禁止并行；失败节点状态不可被改写；恢复必须回放结构化路由。
- **工作区租约会降低并发**：这是有意的正确性取舍；文档说明“同目录串行化”，并给出后续 worktree 隔离方向。
- **排队改变 API 契约**：默认关闭，只有显式开启才返回 202；关闭时保持 409。前后端契约测试锁定两种模式。
- **列表默认 limit 改动**：这是唯一有意的破坏性变更；文档、前端、契约测试与 smoke 同步；第三方客户端迁移说明。
- **只读连接池与 WAL**：SQLite 仍只有一个写者；读池只用于 SELECT；不要在读池上执行写语句；保留 `busy_timeout`。
- **token 用量解析**：不同 CLI 输出形态不同；解析失败留空，不猜测；不内置价格表，避免展示错误成本。
